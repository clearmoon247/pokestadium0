# Bare m2c ranks 801–1000

This batch adds 103 unchanged m2c candidates to the production C registry.
The target was at least 100 new accepted owners; two batches of 100 attempts
produced 103 exact matches. It builds on PR #2's 448 accepted owners at commit
`94838f6629a2a4a4caa68cab029f7acb75988abf`, without repeating its first 800 attempts.

## Method and results

Owners use the existing ascending `(size, empty-return first, assembly path)`
ranking. Every owner received one invocation of stock m2c commit
`c632946b8cfbe8fce442b522dba92dfa72f1f317`:

```text
python tools/m2c/m2c.py -t mips-ido-c --valid-syntax <assembly>
```

There were no m2c modifications, context files, manual C edits, alternate
decompilers, permuter runs, or source variants. The existing runner supplies
primitive-width typedefs and the stock m2c macro header in a separate compilation
unit, leaving each saved candidate byte-for-byte unchanged. It uses the
repository's pinned official IDO 5.3 v1.2 release and existing compiler flags.
Compatibility with these settings is not proof of the original retail compiler.

| Result | Ranks 801–900 | Ranks 901–1000 | Total |
| --- | ---: | ---: | ---: |
| Exact function bytes | 57 | 46 | 103 |
| Byte mismatch | 38 | 29 | 67 |
| C compile failure | 5 | 21 | 26 |
| Link failure | 0 | 4 | 4 |
| Attempts | 100 | 100 | 200 |

The 103 matches cover 4,276 bytes. Ten matched directly in their objects and 93
matched after resolving symbolic relocations with GNU ld. Attempted owners range
from 36 to 48 bytes. All 200 generated candidates and all failure diagnostics are
preserved; the 97 misses remain excluded from production.

The registry now selects 551 C owners and 4,893 assembly owners. Source scaffold
TODOs are unchanged: the production pipeline selects accepted candidate files
directly, rather than treating the scaffold as recovered original source units.

## Validation

The unmodified PR #2 baseline first passed a fresh production build with 448 C
owners on Linux x86-64. After adding the 103 exact candidates, the production
build freshly compiled all 551 C owners, assembled the remaining owners, linked
260 images, and passed the complete-ROM comparison. A direct `cmp` against the
supplied 16 MiB JP ROM passed as well. Both input and output have SHA-256:

```text
ed9f7cd7da795467c1e2b08ed1f878ff5aed906eae9ffe252074aef7a6703d8b
```

`make test` passed all 46 tests before and after registry integration, including
the scaffold regeneration check. Each of the 200 saved candidates was regenerated
from stock m2c and compared byte-for-byte, with its recorded SHA-256 checked
independently. Stock m2c has a clean worktree. The compiler and binutils identities,
accepted source hashes, registry hash, and build-tool hashes are recorded in the
fresh production receipt.

## Reproduction

After providing the verified private ROM and running `make init`, clone stock
m2c into ignored `tools/m2c`, check out the recorded revision, and run:

```powershell
.venv/bin/python tools/m2c_easiest.py --cc tools/ido5.3/cc --start 800 --count 100 --link
.venv/bin/python tools/m2c_easiest.py --cc tools/ido5.3/cc --start 900 --count 100 --link
make rom JOBS=8
make test
cmp baseroms/jp/baserom.z64 build/pokestadium0-jp.z64
```

These commands assume the documented Linux environment, including GNU `cmp`.
The registry is already populated with this batch's exact matches. The standalone
runner records function-level evidence only; the separate production build
provides the full-ROM gate.

## Sanity check

This verifies the established fixed-layout JP build, not general relayout,
original function boundaries, original translation units, original compiler
provenance, semantic annotation, or runtime behavior. No emulator/runtime checks
were run. Production tools and m2c were not changed. ROMs, extracted assets,
assembly dumps, compiler binaries, objects, and output ROMs remain ignored.
The existing production pipeline's storage and assembly mechanisms were used as
documented, not independently re-audited in this batch.
